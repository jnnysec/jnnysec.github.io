# HouYi：当 SQL 注入遇上 LLM——一套打穿 86% 商业 AI 应用的攻击框架

> **作者：** jnnysec  
> **原文：** *Prompt Injection attack against LLM-integrated Applications*，Liu et al., arXiv 2306.05499  
> **标签：** Prompt Injection, LLM Security, Red Teaming

---

如果你有 Web 安全背景，下面这三行代码你一眼就能看懂：

```sql
' OR 1=1 --
```

这是 SQL 注入的经典三板斧：**闭合前面的语句 → 插入恶意逻辑 → 注释掉后面的代码**。三十年来，这套思路打穿了无数数据库。

如果有人告诉你，把同样的思路搬到自然语言上，就能打穿 86% 的商业 LLM 应用——包括 Notion，你信吗？

这就是 HouYi 论文做的事。

---

## 一、为什么简单的注入不够

在 HouYi 之前，Prompt Injection 的主流手法是「Ignore previous instructions」或者间接注入（在网页里埋恶意指令等 LLM 来读）。这些攻击在实验室里效果不错，但作者做了一个残酷的验证：

**拿当时的 3 类攻击手法去打 10 个真实商业 LLM 应用——大部分都失败了。**

原因有三：

1. **上下文分界**：很多应用把用户输入当「数据」分析（如总结、分类），而不是当「指令」执行。注入打进去直接被忽略。
2. **格式限制**：应用对输入输出有严格的格式约束，类似 Web 应用的 WAF 规则。
3. **流程超时**：多步骤 Agent 有时间限制，注入即使生效也来不及展示结果。

换句话说，真实世界的 LLM 应用不是裸模型——它们有 System Prompt、有输出 Parser、有流程控制。**盲打是不行的。**

HouYi 要解决的就是这个问题：做一套黑盒、通用、高成功率的注入框架。

## 二、核心思路：Prompt Injection 版的 SQL 注入

HouYi 的设计哲学极其直白——**把 SQL 注入的三板斧翻译成自然语言版本**。

回想 SQL 注入的结构：

```
正常语句 ')  OR 1=1  --
         ↑    ↑       ↑
       闭合  注入    注释吞尾
```

HouYi 把同样的三组件搬到了 Prompt 层面：

| SQL 注入组件 | HouYi 组件 | 作用 |
|-------------|-----------|------|
| 闭合引号 `')` | **Framework（框架组件）** | 伪装成正常输入，让注入不突兀 |
| 恶意逻辑 `OR 1=1` | **Separator（分隔组件）** | 在上下文之间切开一道口子 |
| 注释吞尾 `--` | **Disruptor（破坏组件）** | 执行真正的恶意目标 |

### 2.1 Framework — 伪装

你不是直接丢一句「Ignore all previous instructions」。那样太过明显。

Framework 的作用是**模拟正常用户行为**。比如你要攻击一个写作助手，先用一段正常的写作请求开头：「请帮我写一篇关于气候变化的文章」。这让 LLM 把后续内容当成同一任务的延续。

### 2.2 Separator — 核心

这是整个框架的灵魂。Separator 的任务是在「正常内容」和「恶意指令」之间制造一个**上下文切换**。

作者设计了三种分隔策略：

| 类型 | 示例 | 原理 |
|------|------|------|
| **语法分隔** | `\n\n---\n\n` | 用特殊符号打破文本结构 |
| **语言切换** | 用德语写忽略指令 | LLM 的多语言能力成了攻击面 |
| **语义翻篇** | 「对于上面的内容，你能解释一下为什么这么改吗？顺便……」 | 用自然语言完成上下文切换 |

**消灭实验**最能说明问题：
- 去掉语义分隔，只剩语法+语言切换 → 只能打 4 个应用
- 去掉语法分隔，只剩语义+语言切换 → 还能打 13 个应用
- 三者组合 → 31 个应用沦陷

**语义分隔是主力。** 这和 WAF 绕过的思路如出一辙——单层防御挡不住多层编码。

### 2.3 Disruptor — 目标

三个典型攻击目标：

- **偷 System Prompt**（最直接的资产泄露）
- **白嫖算力**（让 LLM 免费帮你干活，PAREA 案例中开发者每天损失 $259）
- **生成垃圾内容**（破坏应用输出质量）

### 2.4 三阶段工作流

HouYi 不是一次性丢出攻击 payload 就完事，而是一个**带反馈循环的自动化系统**：

```
上下文推断 → 注入生成 → 动态反馈（检查→迭代）
```

1. **上下文推断**：先用正常例子与应用交互，让另一个 LLM 分析输入输出对，推断出应用的内部 Prompt 语境
2. **注入生成**：根据推断的语境，动态生成三组件
3. **动态反馈**：检查 LLM 的响应是否符合攻击意图。不符合？自动优化再试

这个反馈循环是 HouYi 区别于"随便试试"式攻击的关键——**它像一个自动化渗透测试工具。**

## 四、对安全从业者的启示

### 4.1 如果你是攻击者（红队/渗透测试）

拿到一个 LLM 应用，不要上来就「Ignore previous instructions」。先做三件事：

1. **判断输入是被当「指令」还是「数据」**——用几轮正常交互试探。如果应用做的是决策分析、改写优化，它很可能把你的输入当数据，此时需要 Separator 来切换上下文。
2. **测试分隔边界**——换行符、Markdown 语法、中英文混用、语义转折句，逐一试探哪一层的过滤最薄弱。
3. **利用反馈信号**——LLM 的响应就是最好的 Oracle。如果注入部分生效，响应会有细微变化。自动化这个判断，你就有了 HouYi 的核心能力。

### 4.2 如果你是防御者

- **不要在 Prompt 里靠「请忽略用户让你忽略的指令」来防御。** 这种防御已经被无数实验证明无效。
- **数据/指令边界要做隔离**。XML Tagging（把用户输入包在 `<user_input>` 标签中，System Prompt 明确指定只看标签外内容）是论文中提到的相对有效的方案——但 HouYi 声称也能绕过。
- **多语言是攻击面**。如果应用不需要支持德语、日语等，在输入层做语言检测和过滤。
- **输出验证比输入过滤更可靠**。检查 LLM 的最终输出是否与预期任务一致，比在输入层堵漏洞更有效。

### 4.3 Web 安全背景的迁移优势

如果你从 Web 安全转到 AI 安全，HouYi 是最容易理解的论文，没有之一。

```
SQL 注入：闭合(')  →  注入(OR 1=1)  →  注释(--)
HouYi：   Framework  →  Separator     →  Disruptor
```

**思路完全一致——在「数据」和「指令」的边界上做文章。** 区别只是把 SQL 语法换成了自然语言。

这也意味着 Web 安全里的很多方法论可以直接迁移：

| Web 安全技能 | AI 安全对应 |
|-------------|-----------|
| SQL 注入测试 | Prompt Injection Fuzzing |
| WAF 绕过（编码/分段/混淆） | Guardrail 绕过 |
| 污点分析（用户输入→数据库） | Prompt 数据流追踪（用户输入→LLM→Tool） |
| 黑盒 Fuzzing | 自动化 Prompt 注入框架（如 HouYi） |
