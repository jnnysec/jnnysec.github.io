## 一句话概述

往 RAG 系统的外部知识库里塞几条精心构造的恶意文本，就能让 LLM 对特定问题输出攻击者想要的假答案——**成功率 90%+，且只需 5 条恶意文本混入百万级数据库**。

是不是很像存储型 XSS？恶意内容存在"服务端"，所有访问者都受影响。只不过这次注入的不是 script 标签，而是藏在向量数据库里的文本。

## 2. 背景：RAG 为什么是攻击面

先快速回顾一下 RAG（Retrieval-Augmented Generation）的工作流程：

```
用户提问 → Embedding 模型编码为向量
       → 在向量数据库中检索 top-k 最相似文档
       → 把检索到的文档拼到 prompt 里当"参考答案"
       → LLM 基于 prompt + 参考答案生成最终回复
```

这套架构几乎是现在所有 AI Agent 产品的标配——Dify、LangChain、Coze、Perplexity、各种企业知识库问答……全在用。

问题出在哪？LLM 对检索到的"参考答案"高度信任。如果知识库本身被污染了，LLM 就会把假信息当成事实，一本正经地胡说八道。

这就是 **PoisonedRAG** 的攻击入口——不攻击 LLM 本身，也不攻击 prompt，而是攻击**上游的知识库**。

---

## 3. 攻击是怎么实现的

### 3.1 两个必要条件

要让一次投毒成功，恶意文本必须同时满足两个条件：

| 条件 | 含义 | 类比 |
|------|------|------|
| **检索条件（Retrieval Condition）** | 恶意文本的向量表示要和目标问题足够相似，排在 top-k 里被捞出来 | SEO——内容要匹配搜索意图 |
| **生成条件（Generation Condition）** | 被当作参考答案喂给 LLM 时，LLM 必须输出攻击者想要的目标答案 | 社会工程——光被看到不够，还得让人信 |

这两个条件天然存在张力：你可以让文本和问题高度相似（满足检索），但 LLM 读完可能不会输出你想要的假答案（不满足生成）。反之亦然。

### 3.2 巧妙的拆分策略：S + I = P 🧠

PoisonedRAG 的核心操作是把恶意文本 **P** 拆成两段：

```
P = S + I

S（Similarity，相似段）：负责满足检索条件
    → 与目标问题语义高度相关的词或短句
    → 让 P 在向量空间中靠近目标问题

I（Information，信息段）：负责满足生成条件
    → LLM 生成的短文，内容是"攻击者想要的假答案"
    → 让 LLM 读完就输出目标答案
```

举个例子——攻击者想让 RAG 系统回答"OpenAI 的 CEO 是谁？"时输出"Tim Cook"：

- **I**：用 LLM 生成一段合理叙述，说 Tim Cook 在 2023 年接管了 OpenAI
- **S**：拼接"OpenAI CEO leadership company head"等关键词
- **P = S + I**：既能在检索时被捞出来（和问题相似），又能在生成时引导 LLM 输出错误答案

**黑盒 vs 白盒**：
- **黑盒场景**：用 LLM 生成 S（让它改写 I 使其与问题更相关）
- **白盒场景**：直接对 S 做梯度优化，让 S ⊕ I 的向量表示逼近目标问题的向量表示，效果更好

### 3.3 投毒途径——比你想象的容易

攻击者往知识库里塞恶意文本，现实途径太多了：

- 知识库来自 **Wikipedia** → 恶意编辑词条（历史上有大量案例）
- 知识库爬取**公开网页** → 建恶意网站，等爬虫来抓
- **企业私域知识库** → 内部威胁注入
- **开源数据集** → 提交恶意 PR（供应链攻击变体）

每一种都和传统安全里的攻击面完美对应。

## 4. 实验结果——数据非常震撼

| 维度 | 数据 |
|------|------|
| **数据集规模** | NQ 数据集，2,681,468 条文本 |
| **黑盒 ASR**（仅 5 条恶意文本） | **97%** |
| **白盒 ASR**（仅 5 条恶意文本） | **~98%** |
| **对比 baseline** | 高出其他攻击方法 **20-40 个百分点** |
| **影响范围** | GPT-4、LLaMA-2、Mistral 等 8 个主流 LLM 全部中招 |
| **防御效果** | Paraphrasing、Perplexity 检测等现有手段效果都不理想 |

5 条恶意文本，混在 260 万条正常数据里，占比不到 **0.0002%**，就能达到 97% 的攻击成功率。这个投入产出比在安全攻击里堪称"暴利"。

## 5. 从 Web 安全视角怎么看

作为一个 Web 安全背景的研究者/工程师，这个攻击让我立刻联想到几个经典攻击类型：

### 5.1 存储型 SQL 注入 → 知识库投毒

```
SQLi：payload 写入数据库 → 应用查询时触发
RAG 投毒：恶意文本写入向量数据库 → Agent 检索时触发
```

逻辑完全一样。只不过 SQLi 的 payload 是 `' OR 1=1 --`，RAG 投毒的 payload 是一段伪装成正常知识的文本。

### 5.2 存储型 XSS → 知识库投毒

```
存储型 XSS：恶意内容存在服务端 → 所有访问者受影响
RAG 投毒：恶意文本在知识库 → 所有提问用户受影响
```

两种攻击都是"一次投毒，影响全局"的存储型攻击。

### 5.3 供应链攻击 → 数据集投毒

攻击者不直接攻击目标系统，而是污染它的上游依赖——开源数据集、Wikipedia、公共语料库。这和 npm 包投毒、PyPI 包投毒完全是一个思路。

## 6. 审计 / 红队检查清单

如果你在做 AI Agent 的安全审计，以下是 PoisonedRAG 启发下应该检查的点：

| # | 检查项 | 对应传统安全类比 |
|---|--------|------------------|
| 1 | **知识库写入权限**——谁有权限往向量数据库写数据？有无审核流程？ | 后台 CMS 发布权限 |
| 2 | **检索结果可信度标注**——Agent 回答时是否标注了信息来源？用户能否区分"模型自己的知识"和"检索来的知识"？ | CSP / 同源策略的信任边界 |
| 3 | **向量数据库的租户隔离**——不同租户的知识库是否物理隔离？共享索引可能导致跨租户投毒 | 多租户数据库的隔离 |
| 4 | **外部数据源的完整性校验**——定期同步 Confluence/Notion 等时，是否校验数据完整性？ | 软件供应链签名验证 |
| 5 | **检索 top-k 的防御性过滤**——是否对检索结果做冗余度校验（如要求多个来源一致才采信）？ | 多方验证 / 共识机制 |

## 写在最后

PoisonedRAG 给我的最大感触是：**AI 安全不是给 LLM 加个围栏就完事了**。RAG 的信任链比传统 Web 应用更长——知识来源、检索模块、LLM 推理，每个环节都是攻击面。而知识库投毒作为一种"数据层的注入攻击"，其隐蔽性（5/260万）和高成功率（97%）的组合，让它成为 Agent 安全领域不可忽视的威胁模型。

对我们这些从 Web 安全转向 AI 安全的人来说，好消息是：**攻击方法论没变，变的只是 payload 的形式。** SQLi、XSS、供应链攻击的思路完全可以直接迁移到 AI Agent 安全的分析框架里。
